## 0. 이 문서 사용법 (Claude Code 필독)
1. **이 문서가 기준이다.** 구현 중 충돌이 생기면 이 PRD를 우선하고, 모호한 부분은 추정하지 말고 `docs/OPEN_QUESTIONS.md`에 기록한 뒤 진행한다.
2. **저장 위치:** 이 파일을 `docs/PRD.md`로 둔다. §11(작업 지침)은 레포 루트 `CLAUDE.md`로 분리/통합한다.
3. **빌드 순서:** §12 로드맵의 Phase / Sprint 순서를 따른다. Phase 0(기반) → Phase 1(대행사 매칭)이 최우선.
4. **완료 기준(DoD):** 각 페이지 명세의 "완료 기준" 항목을 모두 충족해야 그 페이지를 "완료"로 본다.
5. **현행 참조:** 카피·구조·플로우는 현행 `teamfirst.kr`을 1차 레퍼런스로 삼되, §13의 개선 항목을 반영한다.
6. **기존 콘솔 자산:** `console.teamfirst.kr`에 이미 존재하는 자산은 본 PRD 기준으로 재정비한다(폐기가 아니라 흡수).

## 1. 배경 & 목표
### 1.1 배경
- 현재 팀퍼스트 메인 사이트는 **아임웹(Imweb)** 으로 구축되어 있다.
- 아임웹은 (1) 커스터마이징 **자율도가 낮고**, (2) **Claude Code로 코드 수정이 어렵다**.
- 이에 **독립몰(자체 코드베이스)** 로 전환하여 입점사가 직접 사용하는 **운영 콘솔**로 발전시키려 한다.
- 신규 도메인 `console.teamfirst.kr`에 이미 Next.js 기반 초기 골격이 올라가 있다.

### 1.2 비전(Vision)
> **"매칭 요청부터 미팅·계약·정산까지 한 화면(타임라인)에서 완결되는 광고 대행사·마케터 매칭 운영 콘솔."**

### 1.3 목표(Goals)
1. 아임웹의 **전 기능을 동등 이상으로 재현**하고, 코드/디자인 **자율도를 확보**한다.
2. 대행사 매칭의 **신청→RFP→평가표→미팅→계약→정산** 전 과정을 시스템화한다.
3. 브랜드사·대행사·마케터·운영자 **역할별 대시보드**를 제공한다.
4. **기존 네이비 브랜드 아이덴티티를 유지**하면서 반응형·접근성·정보구조를 개선한다.
5. Claude Code가 지속적으로 **빠르게 수정·확장**할 수 있는 구조를 만든다.

### 1.4 성공 지표(Success Metrics)
- 현행 사이트의 공개 페이지/플로우 **100% 커버리지**.
- 매칭 신청 폼 **이탈률 감소**(멀티스텝·자동저장 도입).
- 운영자 수기 개입 최소화.
- 신규 페이지/기능 추가 리드타임 단축.

### 1.5 비목표(Non-Goals)
- 아임웹 쇼핑몰의 실물 커머스(장바구니·주문배송·위시리스트) 풀 재현 — Phase 3 이후로 보류.
- 외부 결제대행(PG) 카드 결제 — 정산은 우선 인보이스/입금 관리 방식.
- 모바일 네이티브 앱.

## 2. 현행 사이트 분석 (teamfirst.kr / Imweb)
### 2.1 비즈니스 모델
- **B2B 매칭 플랫폼.** 브랜드사(광고주)와 검증된 광고 대행사 및 프리랜서 마케터를 연결.
- **브랜드사는 전액 무료.** 모든 수수료는 대행사/마케터 측이 매칭 성사·계약 연장 시 부담.
- 핵심 가치: "아무나 입점 못 한다" — **검증된 파트너**만 노출.

### 2.2 두 개의 매칭 제품
| 제품 | 현행 경로 | 대상 | 핵심 플로우 |
|---|---|---|---|
| **대행사 매칭** (Phase 1) | `/RFP` (= 홈) | 브랜드사 ↔ 광고 대행사 | 신청 → RFP제작 → 평가표 → 미팅 → 계약 |
| **마케터 매칭** (Phase 2) | `/marketermatching` | 브랜드사 ↔ 프리랜서 마케터 | 신청서 → 인터뷰 일정 → 인터뷰·확정 → 입금·협업 |

### 2.3 기능 인벤토리 & 이관 판정
| 영역 | 현행 기능 | 판정 | 비고 |
|---|---|---|---|

| 대행사 매칭 신청 | "대행사 매칭신청" 폼 | 보존+개선 | 멀티스텝으로 재설계 |

## 4. 제품 범위 & 단계 (Scope & Phases)
### Phase 0 — 기반(Foundation)
디자인 시스템, 공통 레이아웃/내비, 인증, DB 스키마 기초, 배포 파이프라인.
### Phase 1 — 대행사 매칭 (최우선) ⭐
대행사 매칭 랜딩, 매칭 신청 멀티스텝 폼, 대행사 입점 신청, RFP 자동 생성, 광고주 대시보드, 대행사 대시보드, 운영자 매칭/심사/평가표, 기본 미팅·계약·정산(인보이스).
### Phase 2 — 마케터 매칭
마케터 랜딩, 프로필/로스터, 사례 CMS, 마케터 입점·심층평가, 인터뷰·확정·입금, 마케터 대시보드.
### Phase 3 — 운영 고도화
전자 계약 서명, 정산 자동화/세금계산서, 알림(이메일·카카오), 리포트, 권한 세분화.

## 6. 핵심 도메인 플로우 (Core Flows)
### 6.1 대행사 매칭 라이프사이클
신청 → 접수·검토 → RFP 생성 → 적합 대행사 매칭+컷오프 → RFP 수신 → 제안 제출 → 평가표 작성 → 비교표 확인·후보 선택 → 미팅 → 계약 → 정산.

### 6.2 매칭 신청서 → RFP 매핑
| 신청 폼 입력 | RFP 항목 |
|---|---|
| 회사/브랜드명, 브랜드 소개 | 표지: 매칭 브랜드명 · 브랜드 소개 |
| 프로젝트 타이틀 | 표지: 프로젝트 타이틀 |
| 모집 배경 | 대행조건: 모집배경 |
| 마케팅 예산 | 대행조건: 마케팅 예산 |
| 대행 기간 | 대행조건: 대행기간 |
| 최우선 마케팅 목표 | 목표 및 제안요청: 최우선 목표 |
| KPI | 목표 및 제안요청: KPI |
| 제안 요청 항목 | 목표 및 제안요청: 제안 요청 항목 |
| 희망 레퍼런스 | 선호 대행사 조건: 희망 레퍼런스 |
| 필수 업무역량 | 선호 대행사 조건: 필수 업무역량 |
| 마케팅 영역 | 선호 대행사 조건: 마케팅 영역 |

### 6.3 매칭 신청 상태 머신
```
DRAFT → SUBMITTED → REVIEWING → RFP_READY → MATCHING
      → PROPOSALS_IN → SCORING → SCORECARD_SHARED
      → MEETING → CONTRACTING → CONTRACTED → SETTLED → CLOSED
                                         └→ CANCELLED(어느 단계든)
```

### 6.4 대행사 입점 & 검증 4기준
1. 실무 기반 업무경험 검증
2. 전문 분야(Special Category) 매칭
3. 대행사 규모 및 안정성 평가
4. 데이터 기반 커뮤니케이션 스킬
입점 기준: 마케팅 경력 5년+ / 1개+ 전문 카테고리 / 포트폴리오 검증 / 업무 수행 서약.

### 6.5 마케터 매칭 플로우(P2 요약)
신청서 → 검토·확정 → 마케터 인터뷰 일정 → 인터뷰·확정 → 입금 → 협업.
카테고리: 퍼포먼스 · 그로스 · 브랜드 · 콘텐츠.

## 7. 페이지별 상세 명세 (Page Specs)
### 7.1 [P1] 대행사 매칭 랜딩 `/`
10개 섹션: 히어로 / 매칭 프로세스(STEP 01~05) / RFP 예시 / 평가표 예시 / 표준 계약서 / 입점 기준 / 검증 시스템 / 왜 최적인가 / 파트너 / 최종 CTA. 반응형, Lighthouse 90+.

### 7.2 [P1] 대행사 매칭 신청 폼 ⭐
멀티스텝(4~5단계) 마법사 + 진행률 + 자동 임시저장(DRAFT) + 단계별 검증.
- Step 1 회사/브랜드 · Step 2 대행 조건 · Step 3 목표·제안요청 · Step 4 선호 대행사 조건 · Step 5 확인·제출.

## 9. 디자인 시스템 (Design System)
> **기존 네이비 브랜드 유지 + 개선.** 밝은 블루 대신 **네이비 #111E38 아이덴티티로 통일**.

### 9.1 컬러 토큰
| 토큰 | 값 | 용도 |
|---|---|---|
| navy-900 (brand/primary) | `#111E38` | 1차 브랜드/버튼/텍스트 강조 |
| navy-950 (secondary) | `#000C31` | 헤더·딥 다크 섹션 배경 |
| ink | `#111827` | 본문 헤딩 텍스트 |
| slate-50 | `#F8FAFC` | 라이트 섹션 배경 |
| border | `#E5E7EB` | 보더/디바이더 |
| accent(blue) | `#2563EB` | 링크/포커스 등 보조 강조(절제) |

### 9.2 타이포그래피
본문 Pretendard Variable(채택 완료), 헤딩/버튼 weight 800. h1 28–40 / h2 26–28 / h3 17–20.

### 9.3 컴포넌트 규격
Primary 버튼 navy `#111E38` 흰 텍스트. 카드 흰 배경 `#E5E7EB` 보더 radius 12px. 섹션 라벨 영문 대문자 트래킹. 스텝퍼 가로형(모바일 세로). 평가표 비교 테이블 첫 열 고정·총점 강조.
> 콘솔(데이터 밀집) 화면은 가독성을 위해 pill 대신 rounded(8px) 버튼 사용 — 마케팅 랜딩만 pill. (DECISIONS D-참조)

### 9.4 레이아웃·반응형·접근성
컨테이너 max-width ~1200px. 모바일 우선. 시맨틱·명도대비 AA·포커스 링·`lang="ko"`. Tailwind + shadcn 스타일 컴포넌트.

## 10. 기술 아키텍처
### 10.1 스택(현 구현)

### 10.2 폴더 구조(현)
`app/(public|client|partner|admin)`, `components/ui`, `lib/{supabase,auth,email,schemas,webhooks}`, `db/migrations`, `docs`.

### 10.3 인증·권한
미들웨어 라우트 그룹 보호 + 서버 액션/RLS 소유권 검증.

숫자 URL → 슬러그 301 리다이렉트 맵. 회원 데이터 이관 가능 여부 확인 필요(OPEN).
